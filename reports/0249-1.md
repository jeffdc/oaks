## How it was built

### Design notes

Built from mix phx.gen.auth (Phoenix 1.8.16, --live, Argon2), then reshaped: the generated code is ours to read, not a library. Kept: users and users_tokens, Scope and @current_scope, the session plug and on_mount, sudo mode, remember-me with weekly token renewal, LiveView disconnect on logout. Removed: registration, email confirmation, magic links, email change and the mailer notifier, since there is no email provider and one editor (with more possible later via the same setup-link invite).

Hardening over the generator: session tokens are stored as SHA-256 hashes (the generator stores them raw); the session cookie got an encryption_salt, http_only and Secure in prod; the remember-me cookie is encrypted rather than signed and always written. LiveView disconnect topics are keyed by the token hash so disconnect_sessions/1 works from DB rows.

Second factor: Oaks.Accounts.SecondFactor wraps NimbleTOTP (30 s periods, one period of drift each way, :since replay protection) and makes 80-bit recovery codes stored as SHA-256 hashes (random codes, so a fast hash is enough). The last TOTP use is updated with a compare-and-set so two racing requests can't both pass; recovery codes are spent with a conditional update_all. Oaks.Accounts.SecretBox encrypts TOTP secrets with AES-256-GCM via :crypto, binding "totp:<user id>" as associated data, with a version byte for future schemes. The key comes from LOGIN_ENCRYPTION_KEY in prod (fixed non-secret keys in dev and test); a missing key warns and keeps the site up, as the API key did.

Setup: create_setup_link/1 creates or reuses the user and a hashed 15-minute setup token. The setup controller moves the token and a fresh secret into the encrypted session and redirects, so the token leaves the address bar and the secret is server-chosen. complete_setup/4 checks the code against the new secret once, then in one transaction claims (deletes) the setup token, sets password and encrypted secret, ends every session and replaces recovery codes, so two submissions can't both complete.

Pages are plain controllers, not LiveViews: each step writes the session cookie, which a controller does directly (the generated LiveViews needed a phx-trigger-action form post). Login is two steps with a five-minute pending login in the session; errors never say which part was wrong. OaksWeb.LoginLimiter uses Hammer 7 (ETS) per IP (fly-client-ip) and per account, attempts counted separately for the password and code steps; limits come from config so tests can lower them. Login codes are filtered from request logs.

The existing LiveViews moved from the @authenticated boolean to @current_scope (done by a sub-agent against helpers defined first). Because the scope is set on the static render, the connected?/1 redirect dance is gone. Articles keep their boolean visibility argument; the JSON API passes false. Unused settings CSS was removed and the old localStorage keys are cleared in the browser. Accounts joins species and taxonomy on the dialyzer skip list for the Ecto.Multi opaque false positive. Rejected: passkeys now (more JS, still needs a fallback), magic links (needs an email provider), Auth0 (multi-user roles we don't need), keeping the API key alongside the login.
