# Done report 1: OaksWeb.Plugs.Analytics records redirect responses (for example the 301 from /list) as page views, so a redirected visit counts twice (2e30)

## What was built

### Summary

Analytics no longer counts redirects as page views. OaksWeb.Plugs.Analytics skips 301/302/303/307/308 responses (304 and 404s still count), and the LiveView TrackPageView hook records a page only once it renders, so a LiveView that redirects from handle_params (synonym species and compare URLs) isn't counted. A redirected visit now counts once, on the page it leads to.

### UI tour

1. Nothing on screen changes; the effect shows in the page_views table and on /analytics.
2. Logged out, open /users/settings/password: it redirects to /users/log-in, and page_views gains one row (/users/log-in, 200), not two.
3. Open /species/alba, then follow a link to a synonym URL such as /species/alba%20var.%20repanda: you land on /species/alba, and no row is added for the synonym URL.
4. Open /this-does-not-exist: one row with status 404, as before.

## How it was built

### Design notes

Plug: OaksWeb.Plugs.Analytics already decides in its register_before_send callback, when conn.status is set, so the fix is one more should_track?/2 clause that returns false for the redirect statuses 301, 302, 303, 307 and 308. I listed the statuses rather than skipping all of 300..399 so 304 Not Modified (a cached revisit, not a redirect) still counts; no route returns a 304 today. Unrouted 404s and controller 200s are tracked as before, now with integration tests for both beside the new redirect test (a logged-out GET /users/settings/password, which 302s to the log-in page). The /list to /species 301 on branch 6b12-site-shell falls under the same rule once that branch merges.

LiveView hook: the same double count happened in OaksWeb.Analytics.TrackPageView. Its :handle_params hook runs before the LiveView's own handle_params/3, so a live navigation to a synonym species or compare URL was recorded, and then the canonical page it push_navigates to was recorded again. Redirects from mount were already fine: LiveView skips handle_params when mount redirects. A dead-render redirect was also fine, because the plug skips LiveView routes and no socket connects. The fix splits the hook in two. The :handle_params hook now only marks a new path as pending (a same-path patch leaves an earlier pending path alone), and a new :after_render hook records the pending path and clears it. LiveView's channel skips rendering when a socket is redirected (maybe_diff returns socket.redirected), so the redirecting URL is never recorded; a handle_params push_patch to another path replaces the pending path, so only the page that renders counts. Assigns changed in after_render don't cause a re-render. I rejected checking socket.redirected inside the hook: the hook runs before the LiveView callback that sets it, and there's no lifecycle stage after handle_params but before render other than after_render itself.

Tests: should_track?/2 unit tests for redirect statuses, and 200 and 404; an integration test that a redirect inserts no row and a controller 200 does; a LiveView test that live-navigates from /species/alba to a synonym URL and records only /species/alba; and the direct unit tests now drive track_navigation/3 then track_pending/1, adding cases for no render, a later render, a patch to a new path and a same-path patch before the render. The route audit test still records one row per public route.

The two fixes are separate commits so the hook change can be split off if Jeff wants it handled differently.
