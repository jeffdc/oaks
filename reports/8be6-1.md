## What was built

### Summary

Error responses now carry the CSP and Phoenix's secure browser headers even when no router pipeline ran (an unmatched route's 404, a request the parsers refuse). The CSP moved from the router into OaksWeb.Plugs.SecurityHeaders, used by the :browser pipeline as before and by the endpoint for error responses.

1. No visible change. Open /no-such-page and check the response headers in the browser's network panel: content-security-policy, x-content-type-options and referrer-policy are present, as on any page.

## How it was built

### Design notes

One module plug, OaksWeb.Plugs.SecurityHeaders: with no option it puts the headers (the :browser pipeline); with :errors (in the endpoint, before the parsers) it registers a before_send that puts them when the status is 400 or more. A before_send survives into Phoenix's error rendering because RenderErrors renders from the router's conn for a NoRouteError and from a WrapperError's conn otherwise, so OaksWeb.Plugs.Parsers now reraises non-API refusals wrapped with its conn. Every response was rejected because the site CSP would break the Swagger UI docs page, which loads from a CDN.

### Decisions made in the session

- **9187** The endpoint puts the security headers on every response with status 400 and up (JSON errors too), not on every response
  Why: Every response would put the site CSP on the API docs' Swagger UI, which loads from a CDN; the headers are harmless on JSON errors
