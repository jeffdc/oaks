## What was built

### Summary

Adds POST /api/private/v1/import (packages:submit): a JSON body with one key per table (sources, species, taxa, species_sources), records checked by their schema changesets and applied in one transaction or not at all, with $ref/$find/id refs between records, per-record errors, an enforced dry run (?dry_run=true returns a 24-hour token bound to the raw body SHA-256, the agent token and the plan; an apply without a matching token gets 428, and one whose result would differ gets 409), and an applied_imports ledger so resends are no-ops. Oaks.Import is the domain entry, Oaks.Import.Tables the registry later model items extend; docs/import.md is the producer guide.

### UI tour

2. Write {"species": [{"scientific_name": "tourensis"}]} to a file and POST it with curl --data-binary @file to http://localhost:4444/api/private/v1/import?dry_run=true (Authorization: Bearer <token>, content-type: application/json): see status dry_run, a summary with one species create, and a dry_run_token.
3. POST the same file to /api/private/v1/import without a dry-run-token header: see 428 "Dry-run first".

## How it was built

### Design notes

The domain side is Oaks.Import (the one public entry: dry_run/2, apply/3 and previously_applied/2) over four internal modules. Oaks.Import.Tables is an explicit registry: each entry names the body key, the schema and its changeset/2, the foreign keys that may point at other records (refs: field => target table), the fields an update may not change, and an optional prepare hook (taxa copies Taxonomy's content_updated_at stamp). Registry order is processing order (sources, species, taxa, species_sources), so a future model adds an entry and nothing else changes.

Oaks.Import.Body checks the decoded body without touching the database and turns it into normalized records: target (:new, {:id, n} or {:find, ...}), plain attrs, and foreign keys as {:id, n} | {:ref, name} | {:find, ...}. It collects every shape error: unknown top-level keys (dry_run gets a hint to use the query param), unknown fields and $ keys, non-list tables, non-object records, id plus $find, and ref problems (duplicate $ref, a ref to another table, a forward ref, a ref nobody defines), checked by walking records in processing order. Shape errors return before any database work.

Oaks.Import.Runner runs the records in one Repo.transact/2. Each record resolves its foreign keys (ids checked to exist, refs looked up in the refs seen so far, $finds run and required to match exactly one row) and its target row, goes through the schema changeset with only the given fields, has immutable-field changes turned into errors, passes through the prepare hook, and is inserted or updated with Ecto.ConstraintError rescued. A failed record marks its ref as failed, so dependents report "refers to X, which has errors". Errors don't stop the run (a failed statement doesn't abort a SQLite transaction), so every record's errors come back. Any errors roll back; a dry run rolls back deliberately with its results; an apply compares the plan digest and, if it matches, writes the applied_imports row and commits. Not Ecto.Multi (stops at the first error, and decision 27eb's dialyzer noise) and not context functions (their own transactions would defeat collecting errors).

The plan digest is SHA-256 of term_to_binary([:deterministic]) of each result's table, index, action, updated row id and changes, with new-row ids left out; foreign keys to records in the body are shown, and hashed, as {"$ref": name}, so the digest doesn't depend on the ids an apply gets. The report gives creates their fields and updates from/to per changed field; created ids appear only in an apply's report.

The ledger (applied_imports: body_sha256 unique, import_id unique nullable) is checked before anything else by dry run and apply, and again inside the immediate transaction. Same body is already_applied; same import_id with another body is a conflict.

The web side: OaksWeb.BodyDigest is a Plug.Parsers body_reader that hashes the raw bytes for the import path only, carrying the hash state in conn.private across {:more, ...} reads. OaksWeb.ImportDryRunToken signs %{b: body hash, t: first 8 bytes of the API token's hashed_token, p: plan digest} as a Phoenix.Token with a 24-hour max_age and verifies it into distinct errors (missing, expired, invalid, body_mismatch, other_token), each with its own 428 message. ImportController checks content-type (415), reads dry_run from the query string only (conn.params would take it from the body), and for an apply checks the ledger, then the token, then runs Import.apply/3; ImportJSON shapes the responses. One Logger.info per apply with the import_id, a 12-character hash prefix and per-table counts.

Rejected: JSON canonicalization of the body (62ae says the exact body), storing dry runs server-side (a stateless token needs no cleanup), binding the token to the user (any of Jeff's agents could apply another's dry run), and having Body accept JSON arrays for list text columns (the forms' input format is the one format, decision recorded).

Deviation from the approved plan: Oaks.Import also exposes previously_applied/2, because the endpoint has to check the ledger before verifying the token, and the token supplies the digest apply/3 needs.
