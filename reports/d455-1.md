## How it was built

### Design notes

Read the 0.5.2 source in deps/tailwind before changing anything: bin_path/1 returns config :path when set, else default_bin_path/1, which is now "tailwind-#{target}-#{version}" under _build (0.4 had no version). Tailwind.install_and_run/2, which mix tailwind calls, installs (downloads from GitHub) whenever File.exists?(bin_path(version)) is false, with no checksum. So with the old Dockerfile path the upgrade would have silently switched production builds to an unverified download (which 0.5.2's httpc header fix would let succeed). The fix keeps the existing approach and renames the ADD target, sha256sum check and chmod to the versioned path.

Dev and CI are unaffected: config/config.exs passes MIX_TAILWIND_PATH (set by flake.nix to the Nix-hashed binary) as :path, which bin_path/1 returns before any default. 0.5's new boot check (per-profile :version is refused when :path is set) doesn't apply because the oaks profile has no :version. No changes to config/config.exs, config/dev.exs (the watcher's install_and_run) or the mix aliases.

check-toolchain: added one check in the script's style that greps every _build/tailwind-<target>-<version> path in the Dockerfile, takes the distinct versions, and compares them to config :tailwind. Using all occurrences rather than only the ADD line means a bump that updates the ADD but misses the sha256sum or chmod line also fails (it shows as "found 4.1.11 4.1.12"); the old unversioned path shows as "found <none>". Tried both cases against copies in a scratch root via CHECK_TOOLCHAIN_ROOT.

Constraint: ~> 0.5 rather than ~> 0.5.2 (decision 0a5b): the lock pins 0.5.2, and the header fix only matters for a download nothing runs.

Rejected: setting ENV MIX_TAILWIND_PATH in the Dockerfile to the ADDed file. It would decouple the build from the package's path naming and also cover arm64 builds, but it goes past the approach Jeff approved, so it is captured as idea 00a0 instead.

Verified: scripts/check-toolchain passes; mix compile --warnings-as-errors and mix assets.build in the Nix shell run tailwind 4.1.12 with no download and no _build/tailwind-* file created. docker build --platform linux/amd64 --target builder (Colima on Apple Silicon) ran through mix assets.deploy and mix release: the sha256 check printed OK, tailwindcss v4.1.12 ran, the log has esbuild's "Downloading" line but none for tailwind, and _build in the image holds only tailwind-linux-x64-musl-4.1.12. BEAM crashes at boot under Colima's amd64 emulation, so that build used a scratch copy of the Dockerfile with one extra line, ENV ERL_FLAGS="+JMsingle true", in the builder stage; the repo Dockerfile is otherwise what was built. The runtime stage was not built.
