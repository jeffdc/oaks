## What was built

### Summary

Saving the taxon edit form no longer clears the taxon's parent. TaxonFormLive's validate handler read the level from the params; the edit form has no level field, so it saw "" against the taxon's level, emptied the parent options, and the parent select submitted "" on save, orphaning the taxon (it left the tree and its page 404'd). It now reads the old and new level from the form's changesets, which hold the taxon's level on edit and the chosen level on new. Logic only, no markup, so the restyled form on 6b12-site-shell takes it by merge. Two LiveView tests: editing a section and a subsection (change a field, then save) keeps the parent and the taxon still resolves at its path, and on the new form changing the level still swaps the parent options.

### UI tour

1. Run the dev server and log in (Log in as dev user).
2. Open /taxonomy, go into a section (e.g. Lobatae > Coccineae) and click its Edit button.
3. The Parent select shows the section's subgenus. Type in the Content box or change the Author, and the Parent select still shows the subgenus, with the other subgenus still listed.
4. Click Save Changes: you land on the section's own page (not a 404), it still sits under its subgenus in the tree, and Edit again shows the same parent.
5. Do the same for a subsection or a complex: its parent stays.
6. Open /taxonomy/new, pick Section then Subsection as the level: the Parent options switch from subgenera to sections.

## How it was built

### Design notes

Root cause: handle_event("validate") decided whether to recompute the parent options by comparing taxon_params["level"] || "" with the previous level (the old changeset's changes[:level], else the taxon's level). The edit form deliberately shows the level as read-only text, so the params never carry a level; the first change event therefore compared "" with e.g. "section", recomputed parent_options_for_level("") (which is []), and re-rendered the parent select with only its prompt. The stored parent was no longer an option, so the browser (and LiveViewTest) submitted the prompt's "" on save, Ecto cast it to nil, and update_taxon wrote parent = NULL. The taxon then had no parent, so child_taxa_query never found it, resolve_path failed and its page 404'd. The new form was unaffected because its level select always sends a level.

Fix: build the validate changeset first and take both levels from changesets with Ecto.Changeset.get_field, the new one from the fresh changeset and the old one from the form's source. get_field falls back to the struct's data, so on edit both are the taxon's level and the options are kept; on new they are the chosen levels, as before (an emptied level is nil, which parent_options_for_level's catch-all maps to []). This is the smallest change that makes the comparison mean "did the level change", and it touches only logic, not markup, so it merges cleanly into the restyled form on 6b12-site-shell.

Why the tests missed it: the fixture taxon is a subgenus, which has no parent field, and the edit tests either submitted without a change event or changed content on that subgenus. The new test edits a section and a subsection from taxon_tree_fixture, fires a change event, checks the parent stays the selected option, saves, and checks the stored parent, resolve_path and the taxon page. A second test guards the new form's level-driven parent options, since the comparison logic changed.

Rejected or deferred: requiring a parent for non-root levels in Taxon.changeset would stop any future orphaning, but that changeset is shared with the import path and the Taxonomy phase may reshape taxa, so it is captured as idea ed7a (with the related idea of keeping a stored parent among the select's options, as the species form does). Dropping a crafted level param on edit in validate was also left out: update_taxon already ignores level on save, and no real form sends one. I checked the other form LiveViews (species, source, species source, article): their validate handlers derive no state from the params, and the species form already keeps a stored taxon value among its options, so none share the bug.
