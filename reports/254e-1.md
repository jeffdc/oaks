## How it was built

### Design notes

Plug.Parsers runs in the endpoint, before the router, and raises for a request it can't take. Phoenix's endpoint catches those and renders them through render_errors, choosing ErrorHTML or ErrorJSON from the accept header (HTML when the client sends none), and neither can know the request was for the private API. So the fix sits where the exception starts: OaksWeb.Plugs.Parsers replaces `plug Plug.Parsers` in the endpoint with the same options. Its init/1 calls Plug.Parsers.init/1 (so every option, including f8f5's body_reader, passes through unchanged) and remembers the JSON length limit; its call/2 calls Plug.Parsers.call/2 and rescues. For a request whose path_info starts with ["api", "private"] and a known Plug refusal (ParseError, RequestTooLargeError, UnsupportedMediaTypeError, BadEncodingError, InvalidQueryError, BadRequestError, TimeoutError) it sends JSON {"error": message} with Plug.Exception.status/1 of the exception and halts; anything else, and every request outside the private API, is re-raised with its stacktrace, so the site and the public API behave exactly as before.

Messages follow the private API's style (whole sentences, as OaksWeb.Plugs.ApiToken's): bad JSON carries Jason's own detail ("unexpected byte at position 13: ..."), which is what an agent needs to find the fault in a large import body, and the 413 names the JSON limit in bytes (8000000, Plug's default; the endpoint sets no length, so nothing about the limits changed).

Rejected: a path check inside ErrorJSON/ErrorHTML (the HTML view would have to emit JSON, and the site's error pages would carry API logic); Plug.ErrorHandler on the router (the exception is raised before the router); rescuing any exception with a 4xx plug_status (it would also swallow adapter errors whose meaning isn't known here); configuring a small test limit (a body just over 8000000 bytes runs fast in Plug's test adapter, and testing the real limit is the point).

The refusal still comes before the token check, as before: a bad body is a 400 or 413 even without a valid token, and doesn't count toward the per-IP failed-attempt limit. The ApiToken moduledoc now points at the new plug for these refusals.

The import endpoint (f8f5) isn't on main yet. Merging it conflicts only in the endpoint's Plug.Parsers block: keep `plug OaksWeb.Plugs.Parsers` with f8f5's `body_reader: {OaksWeb.BodyDigest, :read_body, []}` line. A scratch run of the wrapper with f8f5's BodyDigest showed a good body still gets its SHA-256 in conn.private[:body_sha256] (decision 576d), and bad JSON and an oversized body to /api/private/v1/import get the JSON 400 and 413.

Tests (test/oaks_web/plugs/parsers_test.exs) go through the endpoint: bad JSON is a 400 {"error"} with accept absent, text/html, application/json and */*; a body of 8000000+ bytes is a 413; a query string with invalid UTF-8 is a 400; a urlencoded body with invalid UTF-8 is a 400; a good body still parses (body_params and params) through the plug directly; and bad JSON posted to /api/v1 and /users/log-in still raises a 400 for Phoenix's error pages. The public API's version of the same gap is captured as bug 2d52 rather than fixed here.
