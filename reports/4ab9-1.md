## What was built

### Summary

One-click login for local development: the login page has a Log in as dev user button in dev, which posts to /dev/log-in and logs in as dev@localhost (created on first use) with no password or code. It goes through the normal session code, so editing gates and sudo mode work as in production. The route is compiled in only when dev_routes is set (dev and test); a production build has no /dev route, checked by building in prod and by a test that reads the prod config.

### UI tour

1. Run make dev and open http://localhost:4444/users/log-in: below the email and password form there is a Local development card with a Log in as dev user button.
2. Click it: you land on the home page with a flash saying you are logged in as the dev user (dev@localhost), and editing controls appear.
3. Open Settings: it says Logged in as dev@localhost; Change password and Recovery codes open without asking you to log in again.
4. Log out and visit /settings: the logged-out view still shows, so logged-out pages can be checked locally.

## How it was built

### Design notes

Approach. A dev-only controller, OaksWeb.DevLoginController, with one action that gets or creates dev@localhost through a new public Accounts.get_or_create_user_by_email/1 and logs it in with UserAuth.log_in_user/2. Reusing log_in_user means the session is an ordinary hashed session token with authenticated_at set, honours user_return_to, and needs no changes to the login, scope or sudo code. Accounts' private get_or_create_user (used by create_setup_link) now wraps the public function, so there is one way to create a user by email.

Gate. The route sits in the router inside `if Application.compile_env(:oaks, :dev_routes)`, the Phoenix convention; config/dev.exs already set dev_routes but nothing used it. A release (MIX_ENV=prod) compiles without the route, confirmed with MIX_ENV=prod mix phx.routes. The action also checks the setting at runtime, in case the module is ever routed by mistake. The login template uses a plain "/dev/log-in" path rather than ~p because verified routes warn in a prod build where the route doesn't exist; the button only renders when dev_routes was set at compile time (@dev_login in UserSessionController).

POST, not GET. The button is a form post so the browser pipeline's CSRF check applies; a GET would let any page log a local browser into the dev account. An always-logged-in plug was rejected because it would make logged-out pages untestable locally.

Sudo mode is unchanged: a dev login is recent for 20 minutes, then the security pages send you to the login page, where the button logs in again and returns you. I chose that over special-casing sudo_mode? in dev, which would put a dev branch into production code.

Tests. config/test.exs sets dev_routes: true so the route exists in tests (it can't be tested otherwise). Tests cover login and reuse of the dev user, returning to the page that required login in sudo mode, the button on the login page, the runtime refusal when the setting is off, and Config.Reader on config/config.exs with env :prod showing dev_routes unset.

Verified against a running dev server (scratch database) with curl: POST /dev/log-in with the form's CSRF token returns 302 to /, and /users/settings/password then returns 200.
